# ◈ What Is This?

This GitHub account is the public surface of an evolving **AI-assisted mathematical research and verification laboratory**.

The research currently concentrates on difficult problems involving:

- smooth stationary **Gaussian random fields**
- **persistent homology**
- stochastic and Morse geometry
- critical-point processes
- Kac–Rice analysis
- short-lifetime topological features
- exact and high-precision computation
- machine-assisted proof development
- formal verification with **Lean 4**
- reproducibility and adversarial verification

But the larger experiment is methodological:

> **Can human direction, multiple AI systems, formal proof assistants, exact computation, adversarial testing, and immutable provenance operate together as a serious mathematical research process?**

This workspace is being built to investigate that question in public.

It does not ask readers to trust an AI-generated proof.

**It attempts to make the evidence inspectable.**

# ◈ Central Mathematical Program

## Gaussian Random Fields → Critical Geometry → Persistent Homology

One major research direction studies the statistics and geometry of short-lived topological features generated by smooth stationary Gaussian random fields.

```text
Gaussian Random Field
        │
        ▼
Differential Jets
        │
        ▼
Critical Points
        │
        ├── Maxima
        │
        └── Saddles
        │
        ▼
Merging Geometry
        │
        ▼
Elder-Rule Pairing
        │
        ▼
Persistence Lifetimes
        │
        ▼
Small-Lifetime Asymptotics
```

The difficult part is not merely computing critical-point densities.

Persistent homology introduces a global pairing rule: a local extremum must be associated with the saddle through which its connected component actually merges.

This connects **local Gaussian differential geometry** with **global topological selection**.

The research therefore includes work on:

- Gaussian jet distributions
- covariance and Gram matrices
- conditional Hessian laws
- Kac–Rice formulas
- maximum/saddle typing
- near-collision asymptotics
- singular coordinate charts
- endpoint geometry
- elder-rule selection
- persistence pairing
- exact coefficient calculations
- asymptotic lifetime distributions

Some components have computational, review, or formal evidence.

Other components remain explicitly open.

> **Open obligations are part of the research record rather than something to hide.**

# ◈ Evidence Is Multidimensional

The word **verified** is too ambiguous for serious research.

This workspace separates several different questions:

| Question | Evidence |
|---|---|
| What exact artifact was examined? | Git commit · SHA-256 · manifests |
| Can the computation be reproduced? | deterministic replay · exact arithmetic |
| Does the implementation survive attacks? | negative controls · mutation tests |
| Has a bounded argument been reviewed? | source-bound review |
| Does the formal proposition compile? | Lean 4 |
| Does the proof survive kernel checking? | kernel replay |
| Which assumptions or axioms remain? | dependency + axiom audit |
| Does the formal theorem match the intended theorem? | statement-alignment review |
| Is the complete scientific claim established? | mathematical review + dependency closure |

Therefore:

> **PROVENANCE ≠ REPRODUCTION ≠ FORMAL PROOF ≠ STATEMENT ALIGNMENT ≠ SCIENTIFIC ACCEPTANCE**

Each layer carries its own evidence.

A green CI badge is evidence.

**It is not a theorem.**

A merged pull request is history.

**It is not mathematical acceptance.**

A kernel-checked Lean theorem establishes its formal statement from its formal assumptions.

**It does not automatically establish that the formal statement captures every intended informal claim.**

# ◈ Adversarial Verification

A verifier can itself be wrong.

A test suite can be incomplete.

A proof assistant can verify the wrong formal statement.

A numerical result can be reproducible and still fail to establish the intended theorem.

For that reason, the workspace increasingly uses:

```text
POSITIVE CONTROL
      +
NEGATIVE CONTROL
      +
MUTATION TEST
      +
SOURCE IDENTITY
      +
EXECUTION RECEIPT
      +
REVIEW
```

Verification systems are deliberately challenged with altered statements, broken assumptions, stale evidence, invalid execution paths, or weakened checks.

> **A verification system that cannot reject bad evidence provides weak evidence when it accepts good evidence.**

# ◈ Research Integrity Principles

### 01 — Preserve Provenance

Important evidence should be tied to exact source identities.

### 02 — Preserve Negative Evidence

A failed proof, failed test, rejected estimate, counterexample, or superseded argument can remain scientifically useful.

### 03 — Separate Evidence Types

Numerical evidence is not silently converted into a theorem.

Formal evidence is not silently converted into scientific acceptance.

### 04 — Fail Closed

Where practical, missing or invalid verification evidence should block promotion rather than silently count as success.

### 05 — Make Assumptions Visible

Conditional results remain conditional until their assumptions are established.

### 06 — Do Not Manufacture Independence

Multiple AI systems operating under shared accounts, shared evidence, or shared information exposure do not automatically constitute independent scientific review.

### 07 — Preserve Scope

An accepted lemma does not automatically accept its parent theorem.

A successful computation does not automatically establish its interpretation.

### 08 — Attack the Verifier

Verification infrastructure should have negative controls demonstrating that weakened or corrupted evidence is rejected.

# ◈ Verification Before Authority

This project follows a simple principle:

> **Do not grant authority to the generator. Grant weight to the evidence.**

A human can make a mistake.

An AI model can make a mistake.

A reviewer can miss a defect.

A test can be incomplete.

A numerical experiment can be misleading.

A formal system can faithfully verify the wrong formalization.

No single verification mechanism is therefore treated as sufficient for every question.

Instead, confidence is built from multiple independently meaningful layers:

```text
                    CLAIM
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       SOURCE      ANALYSIS    COMPUTATION
      IDENTITY        │           │
          │           │           ▼
          │           │       REPRODUCTION
          │           │           │
          └───────────┼───────────┘
                      ▼
               ADVERSARIAL TESTS
                      │
                      ▼
                FORMALIZATION
                      │
                      ▼
                 KERNEL CHECK
                      │
                      ▼
              STATEMENT ALIGNMENT
                      │
                      ▼
               SCIENTIFIC REVIEW
                      │
                      ▼
              BOUNDED CONCLUSION
```

Agreement between layers increases confidence.

Disagreement between layers is itself useful information.

# ◈ Failure Is Evidence

This workspace does not treat every failed attempt as disposable.

A failed argument can reveal a missing hypothesis.

A broken numerical bound can expose the wrong asymptotic regime.

A failed formalization can reveal an ambiguous definition.

A negative control can expose a weak verifier.

A counterexample can eliminate an entire proof strategy.

A review marked `AMEND` can be more scientifically valuable than an easy `ACCEPT`.

For that reason:

> **The history of how a claim fails can be almost as important as the history of how it succeeds.**

Where useful, the project preserves:

- rejected arguments
- superseded derivations
- failed verification attempts
- counterexamples
- negative controls
- review objections
- corrected formulas
- provenance of repairs

The objective is not a repository that looks perfect.

The objective is a repository whose **epistemic history can be audited**.

# ◈ Open Research

This workspace is intentionally public where appropriate so that mathematical work can be **inspected rather than merely asserted**.

Researchers, mathematicians, engineers, formal-methods practitioners, and AI-for-mathematics researchers are welcome to:

- inspect evidence
- reproduce computations
- challenge assumptions
- identify gaps
- test verification machinery
- propose alternative arguments
- contribute formalizations
- improve research infrastructure

The goal is not to make research look certain.

The goal is to make it increasingly possible to determine **why a result should—or should not—be trusted**.

---

# ◈ Principles

```text
GENERATE BOLDLY.
VERIFY AGGRESSIVELY.

PRESERVE PROVENANCE.
PRESERVE FAILURES.

SEPARATE EVIDENCE FROM INTERPRETATION.

MAKE ASSUMPTIONS EXPLICIT.

MAKE RESULTS REPRODUCIBLE.

FORMALIZE WHAT CAN BE FORMALIZED.

DO NOT HIDE OPEN OBLIGATIONS.

DO NOT CONFUSE AGREEMENT WITH INDEPENDENCE.

DO NOT CONFUSE A GREEN CHECK WITH A THEOREM.

LET STRONGER EVIDENCE OVERRULE WEAKER CONFIDENCE.
```
